# Travel Guide — 玩吃推荐 + 攻略生成

合成本地向导式推荐与小红书实证攻略：短行程对话里给可执行方案；多日/要攻略时 **默认先粗规划、确认后再** 输出 HTML + PDF + 对话摘要。

**同仓优先级**：若同时存在 `travel-skill` / `xhs-travel-skill`，**一律用本 Skill**，勿并行加载旧流程。

---

## 0. 档位分流（先做）

| 档位 | 何时进入 | 产出 |
|------|----------|------|
| **轻量档** | 明确半天/一天/晚上；只玩/只吃/玩吃；未要求攻略页 | 对话内场景化推荐 |
| **攻略档** | **≥2 天**、要攻略/HTML、自驾游/假期规划、要预算明细 | **先粗规划 → 确认 →** 细研究 → HTML + PDF + 摘要 |
| **工具短答** | 仅天气 / 仅 A→B 路线 / 仅查开放时间票价 | 短答即可，不出 HTML |

边界：

- 「周末去哪」未给天数 → **默认按 2 天进攻略档**（可先一句确认「按两日短途做攻略？」；用户说只要半日/一日再降为轻量）
- 用户明确「做份攻略 / 出 HTML」→ 攻略档（哪怕只有 1 天）
- 缺天数且只像「去哪吃」→ 轻量档

## 1. 统一输入字段

| 字段 | 说明 | 必填 |
|------|------|------|
| `destination` | 城市/景区/区域 | 是 |
| `origin` | 出发城市/地点 | 否；**未答可定稿**，大交通/跨城充电标「待补出发地」 |
| `return_destination` | 返程终点（可与出发地不同） | 否；**未答默认 = origin**；两端都空则标「待补」 |
| `intent` | 想玩 / 想吃 / 都要 / 完整攻略 | 轻量默认「都要」 |
| `days` / `duration` | 天数，或半天/一天/晚上 | 攻略档尽量有 |
| `crowd_preference` | 热闹 / 适中 / 人少 | 否，默认适中（轻量+攻略均适用） |
| `travel_type` | 情侣 / 朋友 / 家庭 / 独行 | 否，默认朋友 |
| `transport` | 自驾 / 高铁 / 飞机 / 房车 等 | 攻略档建议有 |
| `vehicle_type` | 油车 / 混动 / 电车（仅自驾） | 自驾时必问 |
| `ev_range_km` | 电车表显/常用续航（km） | 电车时**必追问数字**，不默认 |
| `budget` | 预算范围 | 否 |
| `dates` | 出行日期 | 攻略档建议有；用于季节/电车折损 |
| `party` | 人数；有无老人/小孩 | 攻略档建议有 |
| `preference` | 题材：自然 / 人文 / 亲子 / 摄影 等 | 否；**管点什么题材**，不管玩吃比重 |
| `content_focus` | 偏景点 / 偏美食 / 均衡 | 否；**管日程玩吃比重**；未答默认均衡 |
| `suitable_for` | 适宜人群标签 | 由同行+研究归纳，非用户必填 |
| `first_time` | 是否第一次 | 否 |
| `known_info` | 图片/文字线索 | 否 |

**字段消歧**：`content_focus` = 玩 vs 吃的时间分配；`preference` = 自然/人文/亲子等题材滤镜。二者同时生效时先定比重再按题材选点。

缺 `destination`：先追问。攻略档用下方**一次问卷**凑齐；唯一硬挡定稿的是电车缺 `ev_range_km`。`origin` 未答不挡定稿。

图文线索：抽风格/已选点/忌口/避坑；不足则声明「按常规偏好规划」。

人流口径见 `reference.md` §3；对用户只说理由与风险，不秀等级字母。

## 2. 轻量档流程

1. 识别：只玩 / 只吃 / 玩+吃  
2. 填字段（可默认）  
3. 筛选：目的地 → **人流偏好映射** → 时长/预算 → 场景适配  
4. 场景化输出（3～5 点，有理由；人流/排队坦诚）

### 输出骨架

- **只玩**：3～5 景点 + 理由 + 人流提醒 + 时间建议  
- **只吃**：3～5 店 + 推荐菜 + 人均 + 排队/时段  
- **玩+吃**：一句总判断 → 1 条主路线 → 1～2 备选 → 避坑  

优先组织：热闹 / 避人流 / 第一次来 / 只有半天 / 一条可执行路线。  
第一次来：勿整条线都偏冷门。

### 可选工具

- 天气、起终点路线（环境有则用，无则经验答并说明）；天气优先 Open-Meteo MCP / HTTP（见 README）  
- 最新开放时间/票价/预约：`web_search` / `web_fetch`

## 3. 攻略档流程

### Phase 1：需求确认（仅此步可交互）

**一次问卷**（已给的跳过；尽量合并成一条消息问完，凑齐后自动跑完不再打断）：

| # | 问项 | 未答默认 / 硬性 |
|---|------|----------------|
| 1 | 目的地 | **必填**，无则只追问此项 |
| 2 | 出发地 `origin` | 可空 → 定稿时大交通/跨城段标「待补出发地」 |
| 2b | 返程终点 `return_destination` | 可空 → **默认等于 origin**；与出发不同时必写入路书末段 |
| 3 | 日期与天数 | 周末未说天数 → 按 2 天 |
| 4 | 是否自驾 → 是则油/混/电 | 未说交通 → 必问是否自驾；电车 → **必须**要 `ev_range_km` 数字才能定稿充电日程 |
| 5 | 同行：人数、老人/小孩、`travel_type` | 默认朋友；有老人/小孩写入约束 |
| 6 | 内容侧重 `content_focus`：偏景点 / 偏美食 / 均衡 | **默认均衡** |
| 7 | 人流 `crowd_preference`：热闹 / 适中 / 人少 | **默认适中** |
| 8 | 题材 `preference`（自然/人文/亲子/摄影等） | 可空 |
| 9 | 预算 | 可空 |

禁止连环追问：除电车续航外，缺项用默认，不拆成多轮。  
用户只说「挺能跑」仍要追问续航公里数；禁止默认 300–400km。

混动：默认按油车；用户强调纯电焦虑再按电车要续航。

适宜人群：不单独逼问四字；从同行+后文研究归纳「适合谁 / 不太适合谁」。

### Phase 2：信息研究（自动）

分两档深度：

| 时机 | 深度 |
|------|------|
| **粗规划前** | 轻量：公开搜索 + 小红书各维少量检索即可；不必拉齐全部详情 |
| **用户确认粗规划后** | 完整：高赞详情+评论、地址核验、预算交叉、电车桩等 |

**小红书优先，公开搜索补充。**（完整研究时按下列执行；粗规划前可缩维）

工具：`check_login_status`、`search_feeds`、`get_feed_detail`；自建另可有 `get_login_qrcode`。

前置：

1. `check_login_status`  
2. 未登录：x-mcp → 提醒插件在线且小红书已登录后重试；自建 → 扫码  
3. 仅当工具不可用且用户明确拒绝接入时，才跳过小红书  
4. 禁止因「上次对话超时」直接跳过；单次超时至少换词重试 2 次  

**`search_feeds` 禁忌**：默认**不要传 `filters`**（易空结果/错筛）；需要筛选时优先换关键词，而非 filters。

搜索维度（每维 1～2 次）：

- `{目的地} 攻略 {天数}天`  
- `{目的地} 避坑 踩雷`  
- `{目的地} 费用 花费 预算`  
- `{目的地} 住宿 酒店推荐`  
- `{目的地} 美食 餐厅`  
- `{目的地} 拍照 打卡`（情侣/摄影时加强）  
- 按侧重加减：`content_focus=偏美食` 时加重美食/餐厅维；`偏景点` 时加重攻略/打卡/小众景；`均衡` 各维都做  
- 适宜人群：按同行加搜，如 `{目的地} 亲子`、`{目的地} 老人 适老`、`{目的地} 情侣`、`{目的地} 带娃 避坑`

高赞前 3～5 篇拉详情+评论；记笔记 ID/作者。重点：实测花费、踩坑、小众玩法、政策、机位、评论纠错。

自驾电车时追加搜索维（有续航后再定关键词）：`{目的地/沿线} 充电桩`、`{高速名/服务区} 超充`、车主常用品牌桩体验与避坑。

#### 公开搜索

票价与开放时间、交通、住宿区间、美食、天气、预约；机票/酒店/门票/餐饮/当地交通等预算区间。  
自驾：停车场/服务区；**电车**：沿线超充/快充密度、服务区充电、景区/酒店是否有桩（标注须出行前用小程序核验空位，不假装实时占用）。

#### 天气与穿衣（有 `dates` 时必做）

1. **优先**用天气 MCP（推荐 Open-Meteo，见 README §3；无需 Key）；无 MCP 时用 Open-Meteo HTTP / 公开检索  
2. 按行程日逐日取：气温区间、天气现象、降水概率/量（有则写）  
3. 预报窗口盖不住的日期（常见于 >16 天）：写 **气候向**（该月典型温湿）+「出行前再核」，**禁止**假装精确到小时  
4. 穿衣：据温差/降水/户外强度给 **一句可执行建议**（如「短袖+薄外套，带伞」）；雷雨/高温/高寒写进当日「重要提醒」  
5. 跨城首日：可注明上午出发地 vs 下午目的地温差（若明显）

#### 融合原则

- 价格：小红书实测 > 平台标价 > 博客估算  
- 踩坑：评论区 > 笔记正文 > 公开搜索  
- 路线：高赞 + 地理交通交叉验证  
- 时效：优先近 6 个月；文内标注来源  

#### 漏路径（小红书失败）

仍应用公开搜索完成攻略，**照常出粗规划 /（确认后）HTML + PDF + 对话摘要**，且必须：

- 摘要首段标明：「本次未用上小红书（原因：未登录 / MCP 不可用 / 搜索失败），以下以公开检索为主」  
- HTML 预算与踩坑处降低「实测」措辞，改为「公开渠道参考」  
- 勿假装引用了小红书笔记  

### Phase 3a：粗规划（默认必停 · 确认闸门）

**默认先出粗规划，等用户确认后再细化与出 HTML/PDF。**

粗规划卡（对话内，≤1 屏为宜）：

1. **定位**：目的地 / 天数 / 侧重 / 同行 / 交通（电车写续航）  
2. **每日主题** + 当天 3～5 个点名（店/景可暂定，**不写**详细时段、导航块、来源行、预算表）  
3. **软避网红**一句：主线口碑向，网红仅可选  
4. **待确认**（可选 1～2 条）：如返程终点、某日取舍  
5. **收尾固定问**：  
   > 若按此方向细化并出 HTML+PDF，回「OK」；要改某天直接说（如「Day2 去掉龙潭」）。若要跳过粗规划、一次出完，说「直接出完整攻略」。

**跳过粗规划**（直接 Phase 3b→4）：用户明确「直接出完整攻略 / 不要粗规划 / 一次出完 / 直接出 HTML」。

**未确认前禁止**：写完整 HTML、打 PDF、大段导航/来源表。

用户 OK 或给了修改意见 → 吸收修改后进入 Phase 3b（可补完整 Phase 2）。

### Phase 3b：细路线（确认后）

分段与主题 → 每天 3～5 点带时段 → 每日亮点与提醒；日程内融入人流偏好与玩吃顺路。

**`content_focus` 比重（未答=均衡）**：

| 侧重 | 日程安排 |
|------|----------|
| 偏景点 | 每天景点为主，餐只安排顺路 1～2 顿（少专程觅食） |
| 偏美食 | 每天 2～3 个餐饮锚点，景点穿插其间且勿排太满 |
| 均衡 | 玩吃大致对半，区域联动、少折返 |

**适宜人群约束**：日程点位需能解释「为何适合当前同行」；冲突时改 gentler 方案或拆「主力线 / 轻松备选」，并在提醒里写明不适合谁。

**选点口径（默认 A · 软避网红）**：

- **主线优先**：本地口碑/复访、能改口味、排队合理、值得停留的风景或体验；同城多篇「本地人/老店」交叉 > 单篇爆款打卡  
- **网红可提但不当主线**：出片机位、纯打卡店可放「可选」并写清排队/人流成本；勿用「必去/人生照」硬推  
- **吃**：能微辣/本地菜单、菜市与居民区店优先于车站/景区步行街网红店  
- **玩**：问「不拍照是否仍值得来」；值得才进主线，否则降为可选或跳过  
- 用户明确要「出片/打卡清单」时再提高网红权重，并口头提醒人流  

**导航与路书（Phase 3b / HTML 必做）**：

- 每个停靠点（景点/餐饮/酒店/充电）写清：  
  - `nav_name`：地图可搜全称  
  - `address`：区+路号或「近某某地标」  
  - `map_hint`：一句怎么找（如「金鱼巷内、地下车库对面」）  
  - 可选深链：高德 `https://uri.amap.com/search?keyword=` + URL 编码后的 nav_name 或 address（无坐标也可）  
- 每日卡片顶部加 **当日天气条**（`.day-weather`：气温/现象/降水 + 穿衣一句 + 数据时效注）再写 **当日路书条**：顺序箭头（A→B→C）+ 段间方式（自驾 xx 分 / 步行 xx 分）+ 停车一句  
- 首日跨城：路书写「出发地 → 目的地首站」；**末日**：若返程终点 ≠ 游玩主城，写清「主城 → 返程城市」里程/充电；若就在主城结束（单程抵达、不返出发地），写「行程结束于{城市}，不返回{出发地}」，**不要**默认安排回出发地  
- **对用户可见文案禁止字段名**：不得出现 `return=`、`origin=`、`content_focus=` 等内部写法；用「行程结束于柳州」「从罗城出发」这类中文  
- 地址以公开检索为准；不确定写「导航搜店名，以门店为准」，禁止编造精确门牌  

**灵感来源标注（Phase 3b / HTML 必做）**：

- 每个重要景点/餐饮/玩法节点尽量带一行 `来源`：可点开的链接优先（小红书 `explore/{id}`、公开攻略 URL）  
- 格式示例：`来源：小红书@作者《标题》` + 链接；或多来源用分号并列  
- **节点旁必留**；文末另加折叠汇总「攻略参考地址」（见 Phase 4），二者并存  
- 仅搜索到标题、详情打不开：可写「小红书搜索『关键词』·《标题》」+ explore 链接（若有）  
- 常识/通用安排可标「综合公开渠道」；**禁止伪造**笔记 ID 或 URL  
- 对话摘要可提一句「节点旁已标灵感来源；文末可展开参考列表」  

**自驾差异**：

| 车型 | 安排要点 |
|------|----------|
| 非自驾 | 大交通 + 城际/市内接驳，不写充电 |
| 油车/混动 | 路段里程、油站/服务区、停车与限行提醒 |
| 电车 | 用 `ev_range_km`：基准单段目标 **≤ 续航×0.7**；按 `dates`/季节加严——冬季或明确高寒/雨雪：**≤ 续航×0.55～0.6**；盛夏空调长高速可略收至 ×0.65。超则插充电节点（服务区/超充），写电量窗口与停留时长；住宿优先有桩；景区可顺带补电写入时段。`origin` 已知才串「出发地→首站」充电，未知则首段标待补 |

电车日程中充电点算正式节点（时间线可见），勿只在文末提一句。

### Phase 4：产出（HTML + PDF + 对话摘要）

**仅在 Phase 3a 已确认（或用户跳过粗规划）后执行。**

1. **HTML**：按模板填侧重/适宜人群/充电/路书/导航，以及节点旁 `SOURCE_*`；预算后、页脚前加折叠「攻略参考地址」；字段写入正文时用中文（禁止 `return=` 等）；**所有 `{{…}}` 占位必须替换干净**。  
   **落盘（cicada 站点）**：写入**本仓库**根目录 `guides/<slug>/index.html`，并写同目录 `meta.json`（`title` / `destination` / `dates` / `summary`）。工作区应为 Next-Aurora/cicada（如 `d:/dveloper/cicada`），**不要**再写入已停用的 `travel-skills`。`slug` 用目的地拼音或 ascii kebab（如 `liuzhou`）。页内悬浮条、章节、天气、待办、插图等同前（见下）。  
   **插图（攻略档默认做）**：  
   - **路线总览（视觉风格）**：只用一处 `.route-overview`。每日一张**独立卡片**（顶图 + **Day 徽章叠在图左上角** + 主题标题 + meta 虚线 + 3～4 要点）。桌面日与日之间用轻量 `›` 分隔符（`.route-day-sep`），**禁止**贯穿徽章的横线/竖线连接。手机竖排卡片、隐藏 `›`。跨城出发并入 Day1 meta。文案：「按日示意，非精确导航」。

   - **攻略参考地址**：去重汇总正文用过的小红书/公开攻略 URL；**不含**高德深链与配图 Wikimedia 图源；无链接的「综合公开渠道」可不列入；打印前用 `beforeprint` 临时展开。  
   - **每日天气**：有日期则填预报或气候向；页内固定一句「出行前再核」；数据来源可写 Open-Meteo / 公开渠道。
   - **行前待办**：携带清单、注意事项、预约/行前准备做成可勾选 `.todo-item`（`data-todo-id`）；`#trip-todos` 设 `data-todo-key`；勾选写入 localStorage；展示「已完成 x / y」。  
   - **插图加量**：总览每天尽量 1 张顶图；正文重要景/吃节点 `.media-figure`（整份攻略建议 **≥ 天数+2** 张可链公开图，忌堆到每段都有）。优先用户提供 → Wikimedia 等并写图源；无可靠图省略，勿裂图；禁止热链小红书原图。小红书只作文案/避坑灵感（节点「来源」链笔记即可）；**配图**优先 Wikimedia Commons / 用户自备 / Openverse 等可标注授权来源的图，勿抓取平台 CDN。

## 4. HTML 规范摘要

**配色方案（三套，默认 A）**：

| 代号 | 名称 | 气质 | 主色方向 |
|------|------|------|----------|
